# 下载与进度

## 核心规则

用户要下载/保存/转 mp4 时，进度必须在**聊天里**可见。终端里跑得再热闹，用户看不到就等于没有反馈——他只看到一个卡住的对话。

超过 30 秒的下载，至少给两次不同的进度更新。

## 标准流程

```bash
# 1. 先探时长和体积（percent 和磁盘预检都要用）
python <技能根>/scripts/probe_media.py "{m3u8}" --json

# 2. 启动（立即返回，不阻塞）
python <技能根>/scripts/download_media.py start --url "{m3u8}" --out "{片名}E01.mp4" \
    --duration {probe 给的秒数} --est-size-mb {probe 给的} [--referer "{播放页}"]

# 3. 之后每轮查一次，把输出直接转述给用户
python <技能根>/scripts/download_media.py status --out "{片名}E01.mp4"
```

`status` 直接吐一句能贴给用户的话：

```text
下载进度：42.8%，已处理 18:43 / 43:45，速度 2.1x，文件 137 MB，预计剩余 12:11
```

不用自己解析进度文件。ffmpeg 的 `out_time_ms` 名字叫 ms、实际单位是微秒（历史遗留），手算差 1000 倍是很容易踩的坑。要机读加 `--json`。

### HLS master 清单

`start` 内置自动下钻：如果 `--url` 是 master playlist（只有各档子流地址、没有分片），脚本会先解析到最高码率的分片清单再交给 ffmpeg，启动时打印 `HLS master 已解析到分片清单：...`。这是为了根治"进程活着但 0% 进度"的死状态——ffmpeg 直接喂 master 在部分源站上会卡在解析阶段。`--no-resolve` 可关。

## 脚本内置的护栏

不用自己再实现一遍：

- **detach**：ffmpeg 脱离会话跑，前台等会把 agent 卡到超时。
- **磁盘预检**：`预估 ×1.2 + 保留 5GB`，不足拒绝启动并 `exit 3`（设计行为，不是 bug）。`--min-free-mb 0` 可关。
- **并发闸**：同目录默认最多 2 个下载，超了 `exit 2`。
- **时长安全帽 + 体积上限**：直播源和循环列表不会自己停，没帽子会写到盘满。
- **看门狗**：墙钟超限强杀失控进程并清 pid 文件。
- **错误日志**：ffmpeg stderr 落到 `{输出名}.log`，失败时 `status` 自动回显最后几行。

## 下"全集"时

- 按**累计**估空间（`N 集 × 单集大小`），不要只按单集估——逐集下载时剩余空间是累减的，按单集估到第 20 集就爆了。
- **逐集串行下载**：一集 `start` → `status` 到完成 → 下一集。并发闸"同目录最多 2 个"是护栏不是指引——多集并行会互抢带宽，让每集都慢且进度难汇报。
- **节奏汇报**：每集完成报一次（`第 3/39 集完成，累计 1.2GB`），集内长下载仍按 30 秒规则报进度。
- **单集失败不中止**：记下失败集继续下一集，全部跑完后统一补试失败集；补试仍失败的在总结里如实列出（`36/39 集成功，第 7/21/33 集失败：{原因}`），不要下到一半整体放弃。

## 并发分片引擎

`start` 默认 `--engine auto`：HLS VOD 清单（有 `#EXT-X-ENDLIST`、非 BYTERANGE）自动走内置并发分片引擎；直播、BYTERANGE、mp4 直链、清单解析失败则回退 ffmpeg 串行。源站普遍按单连接限速，ffmpeg 逐分片串行常被压到 0.5–2x，分片并发在限速源上快数倍。**不要再手写分段下载器**——引擎已内置，手搓命令是历史最高频故障源。

- 并发默认 16（`--seg-concurrency`），代码钳在 1–32。并发指同时在途的连接数，由 I/O 余量决定、**和 CPU 核数无关**；高并发在弱机/HDD 上会撑爆内存换页和随机 I/O 队列。内存 < 8GB 或目标盘是 HDD → 给 4–8。
- 每条连接自带重试 + 指数退避（3 次）；失败分片再自动降并发补试两轮（16→8→2）。
- **全部分片齐了才合并**，脚本强制，残缺分片不会被合出来交差。
- 断点续传：失败后重跑**同一条** `start`，已完成分片直接跳过。
- AES-128 加密源不用特殊处理：分片按密文落盘，合并时由 ffmpeg 解密。
- `status` 会多报 `分片 X/Y`；进度、速度、百分比与 ffmpeg 引擎同一套输出，汇报节奏不变。
- 磁盘预检自动按 2.2 倍预估（分片 + 合并输出要同时在盘上）。
- 强制指定：`--engine seg` / `--engine ffmpeg`（对比排查时用）。

## 不要这样做

- 前台跑一条长命令，中间不轮询。
- 用 `subprocess.run(..., capture_output=True)` 包 ffmpeg（拿不到中间进度，还可能因管道写满而死锁）。
- 只把命令卡片停在 Running 就算交代了。
- 重复贴同一句进度而不重新读状态。

## 失败处理

- 分片没下全就**不要合并**（引擎已强制）。`12/2626` 是失败，不是"部分成功"。日志会给出失败分片数和续传提示，先重跑同一条 `start` 续传。
- 下载如果一直进度为0证明这个片源下载不了，这个时候需要重新换源再重新下载。
- 续传两三次仍失败就换源，别在死源上磨。
- 大面积分片失败的常见原因：源站限速、防盗链、分片 URL 过期、并发过高、网络不稳、缺 Referer/UA。
- `status` 若提示"进程存活但尚无任何进度产出，可能卡在打开源开始拉流之前"：通常是源站慢、需防盗链 Referer，或该 m3u8 分片列表与源不兼容。不要等，`stop` 后带 `--referer` 换源重试。
- 合并前检查：分片数、文件非零、顺序、磁盘空间、输出目录可写。
- 输出路径写当前工作目录（即用户会话的工作目录），**绝不写技能目录**（会被技能更新清掉）。
- 收尾时报 `OSError: [Errno 5] Input/output error` 通常是路径/会话层问题，先换稳定路径重试合并，再判定源不可用。
